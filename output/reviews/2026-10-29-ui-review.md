# 부적·방울 UI 변경 검토

### [2026-10-29 오후 - Codex]

검토 요청에 따른 읽기 중심 리뷰다. 게임 소스와 씬은 수정하지 않았다. 저장되지 않은 Unity 편집 내용은 검토 대상에 포함되지 않는다. 검토 범위는 최근 부적 손패 개편·구 배열 제거·방울 슬롯 확장과 관련 씬 연결이며, 게임 전체 규칙의 완전 검증은 아니다.

## 검증 결과

- `dotnet build Assembly-CSharp.csproj --no-restore --verbosity quiet`: 오류 0, 경고 0.
- `dotnet build Assembly-CSharp-Editor.csproj --verbosity quiet --ignore-failed-sources`: 오류 0, 경고 0. 처음에는 --no-restore 실행 시 Editor 프로젝트의 project.assets.json 부재로 실패했고, 정상 복원 후 통과했다.
- test2/test3/SampleScene/Test 저장 씬의 `{fileID: ...}` 로컬 참조: 미해결 참조 0. GUID로 참조하는 모든 외부 에셋의 임포트 유효성까지 검증했다는 뜻은 아니다.
- 제거 요청한 손패 이름/설명/사용 버튼 구 배열과 접근자는 관련 런타임 소스에서 제거됨.
- 방울 획득·구매 한도는 OpenSlots를 사용하고 기본 4, 확장 최대 8 경로 및 5~8칸 두 줄 배치가 구현됨. 새 런 초기화 경로도 존재함. 확장 아이템 정의는 추가되지 않음.
- Unity Play 및 마우스 입력을 통한 실재현은 하지 못했다. 이하 코드는 정적 분석, 씬 항목은 저장 파일 검사 결과다.

## 1. 드래그 종료가 클릭으로도 처리될 수 있음 — 코드 수정 권장

위치: `Assets/Scripts/UI/TalismanCardUI.cs` OnBeginDrag(58), OnPointerClick(53).

드래그 시작에서 클릭 자격을 취소하지 않고, OnPointerClick도 드래그 이력을 검사하지 않는다. 같은 GameObject에 Button과 IDragHandler가 붙어 있으므로 pointerPress와 pointerDrag가 같을 수 있다. 현재 프로젝트의 InputSystemUIInputModule은 이 경우 드래그 시작만으로 eligibleForClick을 취소하지 않으며, 해제 시 클릭을 OnEndDrag보다 먼저 전달한다. 따라서 움직인 카드 위에서 놓으면 설명 클릭과 드래그 종료가 함께 실행될 수 있다. 현재 test3는 InputSystemUIInputModule을 사용한다.

권장: 드래그 시작에서 eventData.eligibleForClick=false를 명시하고 클릭/드래그 분리 조건을 보완한다. 영역 밖 취소 시 설명창이 다시 열리지 않는지와, 성공 드롭 시 부적이 한 번만 사용되는지 Play 검증한다.

## 2. 설명창 Pivot이 카드 위 배치 계산과 맞지 않음 — 씬 설정 수정 필요

위치: `Assets/Scripts/UI/TalismanHandUI.cs` PositionDescription(170), test3의 DescriptionPanel(RectTransform 1529063604).

코드는 카드 상단 + descriptionOffset을 설명창 anchoredPosition으로 설정한다. 저장된 test3 설명창은 높이 285, Pivot=(0.5,0.5)다. 현재 기본 offset=8이면 창이 위로만 펼쳐지지 않고 카드 상단보다 약 134.5 UI 단위 아래까지 내려와 카드를 가릴 수 있다(상하 Clamp가 추가 개입하지 않는 경우).

권장: DescriptionPanel의 Anchor 가운데/Pivot=(0.5,0)으로 연결 규약을 맞추거나, 코드가 Pivot과 높이를 반영해 창의 아래 모서리를 카드 위에 배치하도록 한다.

## 3. 방울 8칸 코드는 있으나 씬 연결은 아직 4칸 — 설정 작업 미완료

위치: test3의 EquippedBellUI.equipBellSlots 및 ShopScreenUI.shopBellSlots.

- test3 equipBellSlots: 직렬화 배열 길이 4, 연결 0개.
- test3 shopBellSlots: 배열 길이 4, 연결 4개.
- test2 equipBellSlots/shopBellSlots도 각각 길이 4.

소스의 new BellSlotUI[8] 선언만 바꿔도 기존 씬의 직렬화 배열 길이는 8로 자동 교체되지 않는다. 이 상태에서 OpenSlots를 8로 늘리면 전투 표시가 없거나 5~8번째 장착 방울의 표시/판매 UI가 누락된다.

권장: 실제 사용 씬의 전투·상점 장착/판매 배열을 8로 확장하고 각 BellSlotUI를 연결한다. 구매 후보 배열은 4 유지. slotContainer도 명시 연결한다. 확장 전후와 5번째 이후 아이템 판매를 확인한다.

## 4. 카드의 Awake 이전에 홈 위치 기록이 실패하면 재시도하지 않음 — 초기화 취약점

위치: TalismanCardUI.Awake(25)/CaptureHome(35), TalismanHandUI.PrepareCards(65).

RectTransform 캐시는 Awake에서만 얻고, CaptureHome은 캐시가 null이면 반환한다. 그런데 PrepareCards는 먼저 cardsPrepared=true로 설정하고 한 번만 캡처한다. 매니저 Awake가 GamePanel을 끄고 Start에서 UI를 갱신하므로, 카드 Awake가 아직 실행되지 않은 순서나 처음부터 비활성인 카드에서는 homeY/homeSibling을 기록하지 못한 채 끝날 수 있다. 이후 드래그의 형제 순서 복구가 생략되거나 기본 위치가 달라질 수 있다.

권장: CaptureHome이 자체적으로 RectTransform을 확보하게 하고, 슬롯을 실제 활성화할 때 아직 기록되지 않은 홈 정보를 캡처한다. 처음부터 숨긴 카드, 나중에 획득한 카드, 시작 화면부터 진입한 카드 모두 확인한다.

## 5. 부모 Scale 변경 시 드래그 거리 불일치 가능 — 조건부 코드 취약점

위치: TalismanCardUI.OnDrag(65).

화면 delta를 Canvas.scaleFactor로만 나누므로 중간 부모의 Scale·회전은 반영되지 않는다. 현재 저장된 test3의 GamePanel/TalismanPanel/CardContainer Scale은 1이라 이 조건은 현재 확인된 배치에는 해당하지 않는다. 추후 부모를 3배 확대하면 카드가 마우스보다 빠르게 움직일 수 있다.

권장: 부모 RectTransform에 대한 스크린 좌표→로컬 좌표 변환으로 드래그를 구현한다. Scale 1/3과 Canvas 배율 변경에서 확인한다.

## 6. 실제 빌드 대상 씬 확인 필요

EditorBuildSettings에는 SampleScene만 활성화되어 있고 test3는 포함되어 있지 않다. SampleScene에는 연결된 새 손패 카드가 없어 지금 만든 test3 화면과 같은 상태로 빌드되지 않는다. 사용자의 작업/출시 씬을 확인한 뒤 빌드 목록을 변경해야 한다. 이번 리뷰에서는 변경하지 않았다.

## 추가 주의

- test2 손패 카드에는 UseTalismanN OnClick 10개가 남아 있다. 현재 test3는 0개다. test2에도 새 설명/드롭 UI를 연결할 때는 즉시 사용 OnClick을 제거해야 한다.
- test3 카드 제목 Text 10개의 Raycast Target은 켜져 있다. 같은 카드 부모로 이벤트가 전달될 수 있으므로 이것만으로 현재 클릭 불가라고 단정할 수 없다. 불필요한 히트 대상 감소를 위해 끄는 것을 권장한다. 설명창 두 Text는 이미 꺼져 있다.
- 방울 확장 효과의 수단과 지속 범위는 미확정이다. 현재 런 단위 변수와 리셋 경로의 존재를 확인했을 뿐, 이 범위를 새로운 확정 규칙으로 승인한 것은 아니다.
